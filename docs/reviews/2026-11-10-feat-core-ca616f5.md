## 계약 대조 (332498f Q1)
- **키 문자열**: JS `stateKey`는 `core.js keyOf`와 필드 순서가 같고, 상태만 enum 번호(Play 0, Choose 1, Win 2, Lose 3)로 쓴다. C# `Rules.Key`(`(int)s.Status`, `Flipped ? '1' : '0'`)와 같다.
  - 목록은 양쪽 다 오름차순이고(JS `add`가 정렬, C#도 정렬), 쉼표로 잇는다. JS 배열의 템플릿 문자열 변환도 공백 없는 쉼표다.
  - 그래서 바이트 단위로 같다. 골든은 선돌이 하나뿐이니, C# 쪽 골든 테스트를 둘 때 선돌·다리가 둘 이상인 상태도 하나 넣으면 정렬까지 고정된다(선택).
- **해시**: JS `Math.imul(h, 16777619) >>> 0`과 C# `uint` 곱셈은 같은 32비트 결과다. C# `QaReplay.StateHash`와 같다.
- **`bodiesUsed`**: JS `bodies - 남은 + (lose ? 0 : 1)`와 C# `Min(Stars.BodiesUsed, Bodies)`는 같은 값이다(패배면 `Bodies = 0`).
- **`!` 기록 조건**: 하네스는 `s0.prev`가 있을 때만 `!`를 기록하고 센다. 게임의 `AttemptCounts.After`(`u.Prev.Prev != null`, 즉 재시작 직전 상태에 Prev가 있음)와 같다.

## 해답 노출 (없음)
- **import**: `core.js`(규칙·`stars`)와 `levels.js`만 가져온다. 솔버를 가져오지 않는다.
- **`expected.minBodies`**: levels.json에서 읽지만 별 계산에만 쓰고 출력하지 않는다. 클리어 때의 별은 게임과 같은 정보다.
- **화면(`show`·`view`)**: 맵, 이야기, levels.js 힌트 문구, 현재 형제의 발자국, 문 상태, 카운터만 나온다. 리플레이·최소 입력·`expected`는 없다.
- **`verify`**: 이미 기록된 줄과 다시 실행한 결과의 차이만 출력한다.
- 하네스의 H는 솔버 경로가 아닌 힌트 문구만 보여 주고, 문서 3절에 이것이 게임과 다르다고 적혀 있다(블라인드 QA). 별 영향(★1)은 같다.

## C# QaReplay가 v1에 맞춰 고칠 것 (scene-flow, 332498f 후속)
- **S1 필드 추가**: `QaAttemptRecord`에 `v`, `from`, `keeps`, `switches`, `levelUndos`, `levelHints`, `levelRestarts`, `stateKey`, `failReason`을 비교용으로 더한다.
- **S2 세는 범위**: v1에서 `steps`/`undos`/`hints`(그리고 `keeps`/`switches`)는 `inputs[from:]`만 센다. 지금 C#은 `inputs` 전체를 센다. 전체 누계는 `level*` 필드와 비교하고, 별은 누계로 계산한다(지금 `Stars.Of(..., counts...)`가 누계라서 맞다).
- **S3 효과 없는 토큰은 불일치**: v1 3절에 따르면 효과 없는 토큰이 나오면 불일치다. 지금 헤드리스 세션은 세 경우를 모두 놓친다.
  - 막힌 이동은 `Feedback`이 되어 `rejected`로 세기만 한다.
  - 되돌릴 것이 없는 `Z`는 `Ignored`가 되어 아무 업데이트도 없다.
  - Prev가 없는 상태의 `!`는 `Rules.Dispatch`가 새 `NewState`를 돌려주므로 `Applied`로 지나간다.
  - `Send` 반환값(`Rejected`/`Ignored`)과, `!` 직전 `State.Prev == null` 여부를 확인하면 된다.
- **S4 `failReason`**: 마지막 명령의 이벤트 중 형제를 잃은 것(`Fall`/`Bridge`/`Seal`/`Vanish`/`Stone`의 마지막)과 비교한다.
- **골든**: 스테이지 29 `R!HDURRRRRKZKDDR` → `10|29|3|2|15|||0|1` / `e57f027f`를 EditMode 테스트로 고정한다.
- **참고**: v1 줄의 `"stars":null`, `"failReason":null`을 `JsonUtility`가 읽으면 int는 0이 될 수 있다(-1이 아님). `stars`는 clear일 때만 비교하니 지금은 문제없다. 새 int 필드는 `null`이 오지 않는 것만 고른다.

## level-design 5fe429a (집계 해석 일치)
- **포기 표시 줄**: `gave_up`이면서 `steps + keeps + switches + undos + hints`가 모두 0인 줄로 판정한다. 문서 4절과 같다.
- **클리어 입력 수**: 마지막 `!` 뒤의 `U D L R K X` 수로 센다(Z·H 제외). 문서 3절의 "inputs는 세션 시작부터"와 맞는 해석이다.
  - 주의: 마지막 `!` 뒤에는 그 판에서 졌다가 `Z`로 이어 간 앞 시도의 이동, 그리고 되돌린 이동도 들어 있다. 그래서 이 값은 "그 판에서 누른 입력 수"이지 최소 입력과 같은 척도가 아니다.
  - 지표로 쓸 때 이 뜻을 `qa-1.md`에 한 줄 적어 두면 좋다(막지 않음).
