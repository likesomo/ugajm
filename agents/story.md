## 고정된 설정 (바꾸지 않는다)
- **주인공**: 스톤헨지(선돌 원형 제단)를 찾아가는 세쌍둥이 방랑자다.
  - 얼굴 없는 후드를 쓴다.
  - 머플러 색은 첫째 청록 #568C88, 둘째 황토 #B99A57, 셋째 테라코타 #B96C59다.
  - 몸은 3개(상한)다.
- **7행성**(챕터 = 행성 = 북두칠성의 별): moss 1–7, hollow 8–14, carved 15–21, frost 22–28, joinery 29–35, crumble 36–42, altar 43–50.
  - 국자는 1-2-3-4-1, 자루는 4-5-6-7이다.
- **7번 이동**: 1~6번째 걸음은 지나가고, 7번째 걸음만 세상을 바꾼다.
- **명령의 의미**:
  - KEEP: 형제가 선돌로 남아 길이 된다(흔적이 도구다).
  - SWITCH: 다른 형제에게 바통을 넘긴다.
  - 구멍: 몸이 다리가 된다.
- **별 흔적**(승인됨, 구현 예정): 걸음마다 형제 색 별빛이 남는다.
  - 7번째 칸은 별 문양으로 깨어난다.
  - 형제의 경로가 별자리가 되고, KEEP 선돌 위에 별이 남는다.
  - 피날레에서 별자리를 보여 준다.
- **3별 B안**과 **잠금 없는 행성 선택**.
- 컷신은 없다(GDD 안티 필러). 이야기는 짧은 문구, 정지 이미지, 연출로만 전한다.
- 한국어와 영어 둘 다 쓴다. 손글씨 UI이고, 한국어 폰트 Gaegu는 2,350자 제한이 있다(GlyphCheck).
- 실존 유적과 종교는 재현하지 않는다. 특정 영화나 게임 캐릭터를 연상시키지 않는다.

## 1단계: 플롯 구조와 형식 설계 (`design/story/narrative-structure.md`)
1. **서사 구조 리서치**(웹 검색, 출처 URL 필수)
   - 대사가 적은 퍼즐 게임과 환경 서사, 짧은 문구로 전하는 서사 기법을 조사한다.
   - 다음 구조 중 이 게임(7행성 × 7스테이지, 7걸음 규칙, 3형제)에 맞는 것을 비교하고 고른다.
     - 3막
     - 기승전결
     - 영웅의 여정
     - 7단계 구조(7과 맞물리는 구조)
     - 순환 서사
   - 기존 게임은 기법 분석용으로만 쓰고, 내용을 모방하지 않는다.
2. **플롯 구조 확정**
   - 거시: 7행성 = 7비트. 각 행성이 이야기의 어떤 단계(발단, 시련, 상실, 전환, 절정, 귀환 등)인지 정한다.
   - 중간: 행성 하나 = 7스테이지. 행성 내부 곡선은 레벨 디자인의 "소개 → 응용 → 반전 → 피날레"와 맞춘다.
   - 미시: 한 스테이지 = 7걸음. 걸음 1~6은 준비이고 7번째는 전환이다. 이 리듬을 문구 쓰는 법에 반영한다.
   - **7의 반복**(7행성, 7스테이지, 7걸음)과 **3의 반복**(3형제, 3별)을 구조 장치로 쓰는 법을 정한다.
3. **형제 캐릭터 설계**
   - 셋의 성격, 동기, 말투(문구 톤)를 정한다. 다음을 지킨다.
     - 얼굴은 없지만 머플러 색, 걸음 리듬, 짧은 독백 톤으로만 구분한다.
     - 형제 관계의 변화 곡선을 둔다.
     - 누가 언제 선돌이 되는가는 플레이어 선택이므로, 특정 형제에 고정된 희생 서사를 강요하지 않는다. 플레이어가 고른 KEEP을 이야기가 받아 주는 방식을 설계한다.
4. **형식(포맷) 규칙**
   - 전달 지점과 각 지점의 글자 수, 톤, 시점, 시제를 정한다.
     - 타이틀 한 줄
     - 행성 진입 카드(제목 + 2줄)
     - 스테이지 한 줄(이야기, 힌트와 별개)
     - 7번째 걸음 순간 반응
     - KEEP, SWITCH, 구멍 순간 한 줄 풀
     - 피날레 결과 문구
     - 별자리 완성 문구
     - 엔딩(정지 이미지 + 문구 시퀀스)
     - 로딩 문구 풀
     - 별지도(행성 선택) 설명
   - 글자 수 기준: ko와 en 각각, UI 폭 기준(ui-layout-fix와 UiLayoutCheck).
   - 용어집: 선돌, 형제, 구멍, 별지도, 관측자 등 ko/en 대응.
   - 변수 문구 규칙: 예를 들어 "{brother}가 선돌로 남았다"처럼 KEEP한 형제 색에 따라 바뀌는 문구가 가능한지, 다국어 조사 처리 방법을 정한다.

## 3단계: 게임 반영 구조 설계 (`design/story/story-integration.md`)
1. **데이터 구조**
   - `Data/story.json`(또는 chapters.json과 levels.json 확장)의 스키마를 정한다.
     - 행성 비트
     - 문구 풀
     - 트리거 조건(첫 진입, 첫 KEEP, 7번째 걸음, 피날레, 별 개수 조건 등)
     - 다국어 키
     - 연결 이미지 키(세계관 시안 장면)
   - export 단정적 검증 항목: 모든 키에 ko와 en이 있음, 글자 수 상한, GlyphCheck, 트리거 유효.
2. **트리거 표**: GameSession과 AppFlow 이벤트에서 이야기 전달 지점으로 가는 표를 만든다.
   - 이벤트: 걸음, 7번째, KEEP, SWITCH, Fall, Undo, Restart, Clear, 스테이지와 행성 진입, 피날레, 전 행성 완료
   - 별 흔적 연출과의 연결: 피날레 별자리, KEEP 선돌의 별
3. **코드 구조 제안**(MVC와 단정적 프로그래밍, `docs/architecture.md` 9장 준수)
   - Model: `StoryCatalog`(순수 C#, 데이터 로드와 검증), `StoryProgress`(본 문구, 엔딩 여부를 세이브에 저장)
   - Controller: `StoryDirector`(이벤트 구독 → 전달 지점 결정)
   - View: 챕터 카드, 결과 문구, 엔딩 화면, 로딩 문구
   - 이 구조를 제안한다. 공용 계약 변경은 "API·인터페이스 변경 고지" 절차로 아키텍트에게 요청한다.
4. **화면별 배치**: 각 화면(타이틀, 별지도, 로딩, 챕터 카드, HUD, 결과, 엔딩)에 무엇이 어디에 나오는지 정한다.
   - UiLayoutCheck 규칙을 따르고, 보드와 숫자를 가리지 않는다.
   - 아트(Codex)에 필요한 이미지 목록을 만든다(엔딩, 행성 카드 배경 등). 전달은 코디네이터를 거친다.
5. **텔레메트리**: 엔딩 도달과 스토리 문구 노출 이벤트가 필요하면 백엔드에 제안한다. 개인정보는 넣지 않는다.
6. **이행 계획**: 단계별로 누가 무엇을 하는지(gameplay-ui, scene-flow, architect, level-design, backend, art), 각 단계 테스트, 잼 일정 안 범위와 이후로 미룰 것을 적는다.
