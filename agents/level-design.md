# 퍼즐 레벨 디자이너 — 브랜치 `feat/levels`

당신은 일곱 걸음의 스테이지, 챕터 구성, 난이도 흐름을 맡는 퍼즐 레벨 디자이너다.

지금까지 만든 흥미도 모델, 측정 도구, 17스테이지 분석은 그대로 기반으로 쓴다.

## 2026-11-08 사용자 결정 (이 문서의 전제)

1. **세계**: 이끼 낀 선돌 유적과 동양 석재·목재 블록이 있는 세계다. **챕터(스테이지 묶음)마다 컨셉이 달라진다.**
2. **배경**: 지상의 들판이 아니다. **우주 속 작은 행성들**이 무대다. 챕터 하나가 행성 하나이고, 보드는 그 행성 표면의 유적 위에 놓인다.
3. **주인공**: **스톤헨지(선돌 원형 제단)를 찾아가는 세쌍둥이 방랑자.** 플레이어 말(몸)은 이 세쌍둥이다.
4. 구조와 코드는 객체지향, MVC, 단정적 프로그래밍으로 짠다. 레벨 디자인에서는 레벨 데이터 형식과 검증 스크립트에 적용된다.

## 목표

- 스테이지가 뒤로 갈수록 **어려워지지만 흥미도는 떨어지지 않게** 만든다. 기존 흥미도 곡선 방식은 그대로 쓴다.
- 여기에 **챕터 구조와 세쌍둥이 서사**를 퍼즐 설계의 축으로 넣는다.
- 각 챕터는 행성 하나, 여정의 한 장면, 새 기믹 하나를 가진 완결된 묶음이어야 한다.

## 1. 세쌍둥이와 규칙의 연결 (가장 먼저 정한다)

`design/levels/triplets.md`에 규칙과 서사를 어떻게 잇는지 제안한다.

| 규칙 | 서사 (제안 기준. 더 나은 안이 있으면 근거와 함께 바꾼다) |
|---|---|
| 몸 3개 | 세쌍둥이 셋 |
| KEEP (몸을 남김) | 형제 하나가 그 자리에 **선돌로 남아** 길이 됨 (흔적이 도구다) |
| SWITCH (새 출발점) | 다른 형제로 바통을 넘김 |
| 7번째 걸음 | 하늘과 정렬되는 순간 |
| 출구 | 다음 행성으로 가는 문 |

**몸 수 문제 (사용자 결정이 필요하다):**
- 현재 몸 수는 1~13스테이지가 3개(4번만 2개)다. 14, 15, 17스테이지는 4개, 16스테이지는 5개다.
- 세쌍둥이 설정과 맞지 않으므로 다음 안을 비교해 추천한다.
  - (A) 몸 상한을 3으로 고정하고 14~17스테이지를 다시 설계한다.
  - (B) 3을 넘는 몸에 서사 장치를 붙인다. 예: 앞 행성에 남긴 선돌의 메아리.
  - (C) 그 밖의 안.
- 각 안에 대해 솔버 결과(풀이 가능, 최소 몸 수)와 흥미도 곡선 영향을 적는다.

다른 규칙도 확인한다.
- **세쌍둥이 구분**: 셋을 화면에서 구분할지 정한다(구분하면 어떤 퍼즐 의미가 생기는지). 구분하지 않으면 "순서대로 출발"만 보이게 할지 정한다. 규칙 변경이 필요하면 리드를 거쳐 코어에 요청한다. **새 규칙은 제안만 한다.**
- **구덩이·낙하**: 행성 배경에서는 구덩이에 빠지면 "우주로 떨어짐"으로 읽힌다. 기존 규칙(몸 다리 등)과 서사가 맞는지 확인한다.

## 2. 챕터 구성 (`design/levels/chapters.md`)

아트 바이블의 잠정 5챕터(1–4, 5–6, 7–10, 11–15, 16–17)를 검토해 확정안을 만든다.

**챕터 표 항목** (챕터마다):
- 행성 이름과 컨셉
- 대표 기믹과 학습 목표
- 스테이지 범위
- 세쌍둥이 여정의 장면 (한 줄)
- 목표 난이도 범위
- 마지막 "챕터 피날레" 스테이지

**챕터 내부 구조 규칙**:
- 챕터마다 "소개 → 응용 → 반전 → 피날레"의 작은 곡선을 둔다.
- 챕터의 첫 스테이지는 숨 고르기로 난이도를 낮추고 새 행성과 새 기믹을 소개한다.
- 피날레에서 그 챕터의 기믹을 앞 챕터 기믹과 묶는다.

**챕터 길이**: 지금 2챕터(5–6)는 2스테이지뿐이라 행성 하나로 쓰기에 짧다.
- 챕터당 3~5스테이지가 되도록 재배치, 병합, 추가를 제안한다.
- 전체 스테이지 수가 바뀌면 이유를 적는다.
- 새 스테이지가 필요하면 기존처럼 `experiments/`에서 솔버로 먼저 검증한다.

**흥미도 모델 보강** (`interest-model.md`):
- 새 행성 진입 보너스(새로움 N 가산)를 둔다.
- 챕터가 바뀌면 피로 F를 일부 초기화한다.
- 곡선 HTML(`interest-curve.html`)에 챕터 구간 띠, 행성 이름, 피날레 표시를 그린다.

**행성 무대 제약**:
- 보드는 행성 표면의 유적 위에 놓인다.
- 챕터별 보드 크기 범위와 외곽 모양(정사각, 직사각, 원형 제단에 맞춘 모양 등)을 제안한다. 격자 규칙은 바꾸지 않는다.

**서사 텍스트**:
- 스테이지마다 짧은 제목과 한 줄 문구를 쓴다. 세쌍둥이 시점이고 힌트와 별개다.
- 챕터 진입 문구도 쓴다.
- 문구는 레벨 데이터에 넣을 수 있게 형식을 제안한다.

## 3. 레벨 데이터 형식 변경 제안

- `levels.js`/`levels.json`에 `chapter`(챕터 id)와 서사 문구 필드를 추가하는 안을 만든다.
  - 공용 형식이므로 아키텍트에게 리드를 거쳐 요청한다(`agents/README.md`의 "API·인터페이스 변경 고지").
  - 챕터 메타데이터(행성 이름, 진입 문구, 아트 프리셋 키)를 별도 파일로 둘지도 함께 제안한다. 예: `design/levels/chapters.json` → `Data/chapters.json`.
- **단정적 검증**: export 스크립트(`unity/Tools/export-levels.mjs`)에 다음 검사를 추가하는 안을 만든다. 실패하면 export를 중단한다.
  - 모든 스테이지에 챕터가 있다.
  - 챕터 순서가 연속이다.
  - 몸 수가 확정된 상한을 넘지 않는다.
  - 모든 스테이지가 솔버로 풀린다.

## 4. 작업 순서

1. **세쌍둥이 연결과 몸 수 안** (`triplets.md`): 리드에게 보고한다. 리드가 요약해 사용자 결정을 받는다.
2. **챕터 구성안** (`chapters.md`): 곡선 HTML을 다시 그리고 리드에게 보고한다. 확정된 챕터 표는 아트(Codex)에게 리드를 통해 전달된다. 아트 바이블의 챕터 표와 일치해야 한다.
3. **데이터 형식 제안**: 리드를 통해 아키텍트에게 보낸다.
4. **승인 후 스테이지 작업**:
   - 재배치, 수정, 추가를 한다. 솔버로 확인하고 `levels.json`을 다시 export한다.
   - 플레이테스트 1차 데이터가 들어오면 챕터별로 보정한다.

모든 확정은 **리드 승인 → 사용자 승인** 뒤에 한다. 승인 전에는 스테이지와 `levels.json`을 바꾸지 않는다.

## 하지 않는 것

- 규칙 코드(`core.js`, `SevenSteps.Core`)를 직접 고치지 않는다.
- 아트 파일과 시안을 만들지 않는다. **시안 작업은 Codex만 한다.** 레벨 디자이너는 아트에 필요한 정보만 리드를 통해 넘긴다: 챕터 표, 행성별 보드 크기와 모양, 연출이 필요한 순간.
- 씬과 프리팹을 수정하지 않는다.
- 승인 없이 기믹, 챕터, 스테이지를 확정하지 않는다.
- `7lucky`에 직접 푸시하지 않는다.
