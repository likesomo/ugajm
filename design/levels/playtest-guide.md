# 사람 플레이테스트 안내 (50스테이지, Unity WebGL / 웹 프로토타입)

목적: 흥미도 모델(`interest-model.md`)이 예측한 막힘·지루함 지점이 실제와 맞는지 확인하고, 가중치를 보정할 기록(`telemetry-mapping.md`)을 모은다. 그리고 15 숫자 문 보강과 힌트 문구 변경을 할지 7장 기준으로 결정한다.
대상: 50스테이지 7행성(`levels.js`, feat/levels-r1 bd9273b부터. 계획 `stage-plan-50.md`, 곡선 `interest-curve.html`). 테스트에 쓸 빌드 커밋은 리드가 `production/playtest-1-prep.md` A에 정하면 여기에도 적는다. 분석은 스테이지 이름으로 한다(진행 기록 v2·텔레메트리도 이름 기준).

두 빌드는 같은 `levels.js`(Unity는 export한 `levels.json`)와 같은 규칙(C# 이식, `verify`·골든 테스트로 일치 확인)을 쓰고, 같은 스키마로 같은 서버에 기록을 보낸다. 대시보드에서는 **클라이언트 필터**로 나눠 본다.

| | Unity WebGL (본 게임) | 웹 프로토타입 |
|---|---|---|
| 대시보드 `client` | `unity-webgl` | `web-proto` |
| `build` | `0.1.0+<커밋>` (`Application.version`) | `proto-<레벨 해시>` |
| 화면 | 3D 보드, 이동·미끄러짐 트윈 | 2D 격자, 즉시 반영 |
| 시작 | 진행자 링크 `/webgl/?newplayer=1&lang=ko` → 타이틀 → 스테이지 선택 (`?level=1`이면 바로 1번) | 바로 1번 |
| 기록 끄기 | 설정 → "플레이 기록 보내기" (기본 켬) | 화면 아래 "기록 전송 켬/끔" |
| 서버 주소 | 빌드에는 없음(`AppConfig.telemetryEndpoint` 비어 있음). 서버의 `/webgl/`로 열면 자동으로 붙음 | `localhost`면 자동으로 8787 |
| 힌트 문구 | feat/view 5a2180a부터 스테이지 내내 제목 아래에 **상시 표시** | 시작 때 메시지 줄에 나오고, 다른 메시지가 나오면 사라짐 |

조작은 같다: 방향키/WASD/옆 칸 클릭, K KEEP, X SWITCH, Z 되돌리기, R 재시작, H 풀이 보기, `[` `]` 스테이지, Enter 다음. Unity만 Esc = 스테이지 선택.

**어느 쪽으로 할지**: 본 게임 확인이 목적이므로 **Unity WebGL을 기본**으로 하고, 빌드가 깨졌거나 한 대의 PC로 빨리 돌릴 때 웹 프로토타입을 쓴다. 한 테스터는 한 빌드만 한다(두 번째 빌드는 이미 푼 퍼즐이라 기록이 무의미).

## 1. 준비 (진행자)

### 1.1 기록 서버 (공통)

자세한 당일 절차(토큰 만들기, 날짜별 DB)는 `server/README.md` "플레이테스트 날 실행 절차"를 따른다. 요약:

```bash
export PATH="/c/Program Files/nodejs:$PATH"
STATS_TOKEN=<토큰> DB_PATH=server/data/playtest-$(date +%F).sqlite node server/src/index.mjs
#   대시보드      http://localhost:8787/dashboard#token=<토큰>
#   웹 프로토타입  http://localhost:8787/play/
#   Unity WebGL   http://localhost:8787/webgl/     ← Builds/WebGL 을 제공하고 ?telemetry= 를 자동으로 붙인다
```
- 날짜별 DB를 쓰면 가짜 데이터(`fake-data.mjs`)가 섞이지 않는다

### 1.2 Unity WebGL

```bash
unity/Tools/unity.sh build-webgl     # 에디터를 닫고 (Unity 라이선스 필요). → Builds/WebGL/
unity/Tools/unity.sh smoke-webgl     # 보드가 그려지는지 확인 (build-webgl OK만으로는 못 거른다)
#   진행자 링크   http://<서버>:8787/webgl/?newplayer=1&lang=ko   (다른 작업 공간의 빌드면 서버를 WEBGL_DIR=<폴더> 로 실행)
```
- **진행자 링크는 테스터마다 한 번만 연다.** `newplayer=1`은 새 플레이어 ID를 만들고 진행 기록(클리어·최소 몸·별·시작 횟수)을 지운다. 소리 크기·기록 동의·언어 설정은 남는다(gameplay-ui 01795d3). 열리면 주소창에서 `newplayer`가 사라지므로 새로 고침해도 다시 지워지지 않는다
- 영어 확인용은 `lang=en`. `<서버>`는 이 PC면 `localhost`, 같은 와이파이의 다른 기기면 이 PC의 IP
- **itch.io 임베드에서는 URL 인자(`newplayer`, `lang`, `telemetry`)가 먹지 않는다**(iframe). 1차는 itch.io를 쓰지 않고 이 서버의 `/webgl/`로 직접 호스팅한다
- **시작 전 확인·기록**: 설정 화면의 텔레메트리 상태 줄 "보냄 n, 대기 n, 마지막 응답 200, ID xxxxxxxx"를 본다. 1스테이지에서 몇 걸음 움직인 뒤 다시 열어 **보냄 수가 늘고 마지막 응답이 200**인지, 그리고 **ID 앞 8자**를 메모(`TEMPLATE-notes.md` 테스터 블록)에 적는다. "보내지 않음"이면 "플레이 기록 보내기"를 켠다. "연결 안 됨"이나 200이 아니면 서버와 주소를 확인하고 시작하지 않는다
- `unity.sh serve`(8090)로 열 때는 `?telemetry=http://localhost:8787`을 직접 붙여야 기록된다. 테스트에는 `/webgl/`을 쓴다
- 테스트 첫날 한 번: 대시보드의 클라이언트 목록에 `unity-webgl`이 생기고, 메모한 ID 앞 8자의 플레이어가 보이는지 확인한다

### 1.3 공통 주의

- 진행 상황(클리어 기록)과 플레이어 ID는 브라우저 저장소에 남는다. 테스터를 바꿀 때는 **진행자 링크(`newplayer=1`)로 새로 시작**한다. 시크릿 창을 쓴다면 **테스터가 바뀔 때 시크릿 창을 전부 닫고** 새로 연다(창 하나라도 남으면 저장소가 이어진다)
- 한 테스터가 세션을 나눠 이어서 할 때는 `newplayer` 없이 `/webgl/?lang=ko`로 같은 브라우저(시크릿 창이 아닌 프로필)에서 연다. 진행 기록과 ID가 남는다
- 같은 와이파이의 다른 기기는 `http://<이 PC IP>:8787/webgl/`(또는 `/play/`). 원격 테스터는 서버 외부 공개(터널)가 필요하므로 **사용자 승인 후**에만, `https://<터널 주소>/webgl/` (자세한 것은 `server/README.md`)
- 웹 프로토타입만 따로 띄울 때 `python -m http.server 8777`은 이 PC에서 8777 포트가 이미 쓰이고 있을 수 있다. 기록이 필요하면 항상 `/play/`를 쓴다
- 테스트 기간에는 스테이지와 빌드를 바꾸지 않는다. 바꾸면 `build` 값이 달라지므로 빌드 필터로 나눠 본다

## 2. 테스터에게 할 말 (이것만)

> 한 번에 7걸음만 걸을 수 있는 퍼즐입니다. 1번부터 순서대로 해 주세요. "풀이 보기"와 되돌리기는 언제든 써도 됩니다.
> 그만하고 싶으면 그때 그만두셔도 됩니다. 생각나는 건 소리 내어 말해 주세요.

- **규칙을 미리 설명하지 않는다.** 스테이지 시작 때 나오는 안내 문구(이하 "힌트 문구")가 규칙을 가르치는지 보는 것도 테스트다
- "풀이 보기"(H)는 힌트가 아니라 **처음부터의 최단 풀이 전체**를 보여 준다. 대시보드의 "힌트 본 비율"은 이 버튼이다. 힌트 문구를 읽었는지는 기록되지 않으므로 진행자 메모로만 안다
- 막혀도 도와주지 않는다. 테스터가 물으면 "풀이 보기를 써도 돼요"까지만
- 50스테이지는 한 번에 끝내기 어렵다(예상 2~3시간). **한 세션 50~60분**, 끝난 지점을 메모하고 다음 세션은 그 다음 스테이지부터 이어서 한다. 이어서 하려면 1.3처럼 `newplayer` 없는 주소로 같은 브라우저 프로필에서 연다
- 1차는 **회전 배치**(2.1 배정표, 사용자 결정 2026-11-10): 모두 1~14를 한 뒤 테스터 번호별로 정해진 행성의 첫 스테이지로 건너뛴다. 건너뛴 기록은 보정에서 따로 본다. 기록에서 고르는 기준은 `via`가 아니라 "앞 행성 피날레를 깨기 전에 들어왔는가"다(`telemetry-mapping.md` 1장). 지도·목록에서 고른 진입은 첫 스테이지든 이어 하기든 건너뛰기든 모두 `via=select`라서 `via`로는 가를 수 없다. 진행자는 노트에 건너뛴 행성과 시각을 적는다
- 시간 제한을 말하지 않는다
- 목표 인원: **5명 이상** (5명 미만인 스테이지는 보정에 쓰지 않는다)

### 2.1 회전 배정표 (1차, 진행자 PC 현장, 1인 50~60분)

테스트 빌드: `0.1.0+________` (7lucky `________`, ui-layout-fix 병합 뒤 리드가 적음). 장소는 진행자 PC 현장, 같은 와이파이 기기는 `http://<진행자 PC IP>:8787/webgl/`만(외부 공개 없음).

**왜 회전인가**: 1~2장(1~14)이 예상 25~40분이라 한 사람이 1번부터 하면 3장 앞에서 시간이 끝난다. 그래서 1~14는 모두 하고(규칙을 배우는 구간, 5명 모두의 기록), 남은 20~25분을 3~7행성에 나눠 준다.

**5명 기본 (T1~T5)**: 남은 시간을 행성 둘에 나눈다. **행성 A**(시작 행성)를 그 첫 스테이지부터 하고, 정해진 시각이 되면 **행성 B**(다음 행성, 7행성 다음은 3행성으로 돈다)의 첫 스테이지로 넘어간다. 그러면 3~7행성마다 A로 1명, B로 1명, 모두 2명이 들어간다.

| 테스터 | 언어 | 1부: 1→14 | 2부: 행성 A (첫 스테이지부터) | 3부: 행성 B (첫 스테이지부터) | 끝 |
|---|---|---|---|---|---|
| T1 | ko | 0~35분 | 3 새김돌 행성 **15**→ | 4 서리 위성 **22**→ | 57분 |
| T2 | ko | 0~35분 | 4 서리 위성 **22**→ | 5 결구의 행성 **29**→ | 57분 |
| T3 | ko | 0~35분 | 5 결구의 행성 **29**→ | 6 무너지는 행성 **36**→ | 57분 |
| T4 | ko | 0~35분 | 6 무너지는 행성 **36**→ | 7 원형 제단 **43**→ | 57분 |
| T5 | ko | 0~35분 | 7 원형 제단 **43**→ | 3 새김돌 행성 **15**→ | 57분 |

시간 규칙(진행자가 시계를 본다. 테스터에게 시간 제한을 말하지 않음):
- **1부 → 2부**: 14를 깨거나 **35분**이 되면(먼저 오는 쪽) 행성 A로. 35분에 14 전이면 지금 스테이지를 깨거나 그만둘 때까지 기다렸다가 넘긴다(스테이지 중간에 끊지 않는다). 못 한 1~14 번호를 노트에 적는다
- **2부 → 3부**: 2부를 시작하고 **11분**(1부가 빨리 끝났으면 남은 시간의 절반)이 지난 뒤 지금 스테이지가 끝나면 행성 B로. 행성 A를 그 전에 다 깼으면 바로 B
- **끝**: 57분이 지나고 지금 스테이지가 끝나면 멈추고 4장 질문(약 3분). 60분을 넘기지 않는다
- 예상: 행성 A·B에서 각각 2~4스테이지. 즉 5명으로는 **각 행성의 앞부분(첫 스테이지 = 톱니 곡선 질문 G-2)을 2명씩** 본다. 피날레(21, 28, 35, 42, 49, 50)와 막힘 예측 스테이지(33, 41, 42, 49, 50)는 5명으로는 거의 안 닿는다 → 6명째부터, 또는 세션 2로 채운다

**6~10명 (추가 행)**: 추가 테스터는 시간을 나누지 않고 **행성 A 하나를 끝까지** 한다(피날레·막힘 예측 관찰용). 행성 A를 다 깨고 시간이 남으면 다음 행성 첫 스테이지로 넘어간다.

| 테스터 | 언어 | 1부 | 2부: 행성 A (끝까지) | 주로 보는 것 |
|---|---|---|---|---|
| T6 | ko | 1→14 (35분까지) | 7 원형 제단 **43**→50 | 49·50 막힘 |
| T7 | ko | 1→14 (35분까지) | 6 무너지는 행성 **36**→42 | 41·42 막힘 |
| T8 | ko | 1→14 (35분까지) | 5 결구의 행성 **29**→35 | 33·34·35 |
| T9 | ko | 1→14 (35분까지) | 4 서리 위성 **22**→28 | 23 홀수의 셈, 28 피날레 |
| T10 | ko | 1→14 (35분까지) | 3 새김돌 행성 **15**→21 | 15 숫자 문, 21 피날레 |

- 테스터 번호는 **오는 순서대로** T1부터 준다. 번호가 곧 배정이다(사람을 보고 고르지 않는다)
- 같은 테스터가 세션 2를 할 수 있으면: 세션 1에서 멈춘 행성의 **멈춘 스테이지 다음부터** 이어서(같은 브라우저 프로필, `newplayer` 없이). 행성 A를 끝까지 못 한 T1~T5에게 우선 준다

**영어 테스터 (E, 1명)**: 테스터 번호와 따로 센다.
- 영어가 편한 사람 1명을 **E**로 정하고, 나머지에게 T1부터 번호를 준다. E는 `lang=en` 링크로 **1~14만**(문구 길이·잘림·어색한 표현 확인, 35분 안팎). 남은 시간은 영어 그대로 4장 질문 + 문구에 대한 의견. 행성 A·B는 하지 않는다(영어 기록은 `lang`으로 나뉘어 행성 표본에 안 셈)
- 한국어 테스터가 5명이 안 되면 E를 두지 않는다(T1~T5를 먼저 채움). 그때 영어 확인은 진행자가 테스트 전후에 `lang=en` 새 플레이어로 직접 하고, 그 ID 앞 8자를 노트에 "진행자 확인"으로 적어 보정에서 뺀다

**시작 링크** (`<서버>` = `localhost`, 같은 와이파이 기기는 진행자 PC IP):

| 언제 | 주소 | 비고 |
|---|---|---|
| 테스터 시작 (T1~T10) | `http://<서버>:8787/webgl/?newplayer=1&lang=ko` | 테스터마다 한 번. 새 ID·진행 초기화. 타이틀 → 시작 → 1번 |
| 영어 테스터 E | `http://<서버>:8787/webgl/?newplayer=1&lang=en` | |
| 행성 A·B로 건너뛰기 | 게임 안에서: **Esc → 스테이지 선택 → 행성 → 첫 스테이지** | 잠금 없음. 새로 고침하지 않는다(같은 ID·진행 유지, `via=select`) |
| 건너뛰기 예비 (화면에서 못 찾을 때) | `http://<서버>:8787/webgl/?level=22&lang=ko` | `newplayer`를 **붙이지 않는다**(붙이면 ID가 바뀌어 1~14 기록과 끊김). 같은 탭에서 열면 진행·ID 유지, `via=url` |
| 세션 2 이어 하기 | `http://<서버>:8787/webgl/?lang=ko` → 스테이지 선택 | 같은 브라우저 프로필 |

- `?newplayer=1&level=N`처럼 새 플레이어로 바로 뒤 행성을 여는 링크는 **쓰지 않는다**. 1~14 기록과 같은 플레이어로 이어져야 "1~14를 하고 건너뜀"으로 분석된다(`telemetry-mapping.md` 1장 "건너뛴 시도")

## 4. 끝난 뒤 질문 (2분)

1. 가장 재미있던 스테이지와 이유
2. 가장 짜증났던 스테이지와 이유 (억울함 / 지루함 / 몰라서)
3. "아!" 하고 풀린 순간이 있었던 스테이지
4. 규칙 중 끝까지 헷갈린 것
5. 15번(숫자 문)에서 문의 숫자를 셌는가, 그냥 지나갔는가
6. 어느 행성이 가장 기억에 남는가, 어느 행성에서 지쳤는가

답은 `design/levels/playtest/TEMPLATE-notes.md`를 복사해 `design/levels/playtest/<날짜>-notes.md`에 사람별로 적는다(이름 대신 배정표 번호 T1, T2…·E, 빌드 종류 표시). 대시보드의 플레이어와는 설정 상태 줄의 ID 앞 8자와 시작 시각으로 연결한다.

## 5. 기록 넘기기

```bash
T=<토큰>; D=$(date +%F)   # 테스트 당일. 다른 날이면 D=2026-11-12 처럼 직접
mkdir -p reports/telemetry
for C in unity-webgl web-proto; do
  curl -H "Authorization: Bearer $T" "http://localhost:8787/api/export/attempts.csv?client=$C&since=$D" -o reports/telemetry/attempts-$C.csv
  curl -H "Authorization: Bearer $T" "http://localhost:8787/api/export/events.jsonl?client=$C&since=$D" -o reports/telemetry/events-$C.jsonl
done
```
- `since=<날짜>`는 서버 PC 로컬 시간 그날 0시부터다(server 수정, 2026-11-10). 시작 전 확인 기록을 빼려면 `since`에 확인을 마친 시각(epoch ms)을 준다
- `reports/`는 커밋하지 않는다. 레벨 디자인이 보정 스크립트로 읽어 `interest-curve.html`에 실측 I를 겹쳐 그린다
- 두 클라이언트는 같은 스테이지 이름으로 합쳐 본다. 단, 한 스테이지에서 둘의 클리어 시간 중앙값이 2배 넘게 차이 나면 합치지 않고 원인(표시·조작)을 먼저 본다

## 6. 성공 기준 (모델 검증)

- 장 첫 스테이지(8, 15, 22, 29, 36, 43)에서 시간이 앞 장 피날레보다 짧다 → 톱니 곡선 맞음. 길면 새 행성 보너스(N +0.1) 가정이 틀림
- 23 홀수의 셈의 시간·idle이 4·29(몸 2 소개) 수준이다 → 자동 난이도 보정(`dAdj`) 필요
- 29 레버 소개에서 시간·재시작이 28(4장 피날레)보다 크게 뛰지 않는다 → 5장 진입이 매끄러움
- 38~40에서 HUD 석상 수를 보고 푸는가 → 아니면 화면 표시 강화 요청(게임플레이/UI)
- 실제 이탈이 가장 많은 스테이지의 예측 I가 0.45 이하인가 → 아니면 C·F 상수 보정(`telemetry-mapping.md` 3장)
- 별(★2·★3, `stars.md`) 구현이 들어가면 스테이지별 ★3 비율도 본다. ★3이 0/5인 스테이지가 한 장에 몰리면 ★3 조건 완화 검토

## 7. 결정 기준: 15 숫자 문 보강과 힌트 문구 (`proposal-polish.md` 연계)

표본이 5명 안팎이므로 비율 대신 **"5명 중 몇 명"** 으로 판단한다(인원이 늘면 같은 비율로). 첫 시도만 센다. 대시보드 **스테이지 지표 표**와 **히트맵**, 그리고 4장 메모를 같이 본다. 결정은 레벨 디자인이 제안하고 사용자 승인 뒤에 스테이지를 바꾼다.

### 7.1 대시보드에서 볼 값

| 판단 | 대시보드 위치 | 값 |
|---|---|---|
| 15가 너무 쉬움 | 표 "클리어 시간 중앙", "클리어 이동 중앙" / `attempts.csv`의 `activeMs`, `moves`, `minMoves` | 테스터별로 activeMs < 20초 **그리고** moves ≤ 1.3×minMoves 인 사람 수 = **"쉬움 n"** |
| 15에서 문을 시험해 봄 | 히트맵 스테이지 15, 지표 "막힌 이동" | 숫자 문 칸의 막힘 횟수 (0이면 아무도 문 규칙을 건드리지 않음) |
| 29가 실제 급상승 | 표 "클리어 시간 중앙", "재시작/시도", "힌트 본 비율", "이탈률" | 29의 클리어 시간 중앙값 ÷ 28과 30 중 큰 값 = **"29 배율"**, 29에서 풀이 보기·이탈한 사람 수 |
| 힌트 문구가 답을 줌 | 4장 메모 ★ + `attempts.csv`의 `idleCount`, `activeMs` | 문구를 읽은 직후(메모 시각) 30초 안에, 그 사이 idle 없이 푼 사람 수 = **"즉답 n"**. 시각은 메모, idle은 `events.jsonl`의 `idle.t`로 확인 |
| 힌트 문구가 모자람 | 표 "힌트 본 비율", "몸 낭비", "몸 사용 사유" / 히트맵 "몸 낭비" | 풀이 보기·이탈한 사람 수 = **"막힘 n"**, 규칙 오해 흔적(`fell`·`vanish`·`crumble` 뒤 재시작) |

### 7.2 15 숫자 문

50스테이지 순서에서 숫자 문(15)과 레버 소개(29)는 멀리 떨어져 있어, 예전처럼 둘을 묶어 판단하지 않는다.

| 15의 실측 | 결정 |
|---|---|
| 쉬움 ≥ 3/5 **또는** 질문 5에서 "안 셌다" ≥ 3/5 | **15 다듬기**: 몸 1개를 유지하되 숫자 문을 바닥으로 바꾸면 해가 막히도록(문을 세어야 풀리도록) 맵 수정. 3장 첫 스테이지라 쉬워야 하므로 몸 2개로 올리지 않는다 |
| 쉬움 ≤ 2/5 이고 문 칸 막힘 ≥ 1 (누군가 문을 시험함) | **그대로** |
| 그 밖 | 그대로 두고 16~20(몸 2개 숫자 문)에서 숫자 문을 셌는지 메모로 확인 |

- 15를 다듬을 때 확인: 솔버로 풀림, `--strict` 기준으로 숫자 문이 필요, 15·16의 예측 I가 떨어지지 않음
- **29가 막힐 때** (29 배율 ≥ 2 또는 막힘 ≥ 2/5): 29의 문구는 이미 "발판과 달리 한 번 당기면 그대로다"라고 레버와 발판의 차이를 말한다. 메모로 원인을 가른다
  - 레버를 밟았는지, 벽이 내려갔는지 **못 봤다** → 표시 문제. 레버 상태·벽 변화 표시 강화를 게임플레이/UI·아트에 요청
  - 규칙은 알았는데 **몸 2개 계획**에서 막혔다 → 의도한 도전. 이탈 ≤ 1/5면 그대로
  - 이탈 ≥ 2/5 → 5장 순서(29 내리는 벽 → 30 열면 닫힌다 → 31 올려서 멈추기 → 32 레버와 발판)에서 32를 29 앞으로 당기는 안을 검토

### 7.3 힌트 문구

대상은 질문형 시안이 있는 **23 홀수의 셈, 25 멈춰 세우는 선돌**(`proposal-polish.md` 2장)과, 결과에 따라 문구 보강이 필요할 수 있는 규칙 소개 스테이지 **4, 22, 29, 36, 38, 40, 43**이다. 새 스테이지(탐색 후보)의 힌트 문구는 임시 문구라, 막힘이 많으면 그 스테이지도 같은 기준으로 고친다.

| 실측 | 결정 |
|---|---|
| 즉답 ≥ 3/5 이고 막힘 ≤ 1/5 (문구가 답을 말해 버림) | **질문형으로 교체** (23, 25 시안). 규칙 소개 스테이지는 교체하지 않는다 |
| 막힘 ≥ 2/5 (풀이 보기·이탈) | **질문형 금지**. 지금 문구 유지, 3장 메모에서 오해한 규칙이 있으면 그 규칙을 더 직접 말하도록 보강 |
| 규칙 소개 스테이지에서 오해 흔적(같은 사유의 몸 낭비 2회 이상, 또는 `move.crumbled` 직후 재시작)이 있는 사람 ≥ 3/5 | 4·29·36·40의 지금 문구는 모두 규칙을 직접 말한다. 메모에서 "문구를 안 읽었다/못 봤다"면 문구 표시(위치·시간) 문제로 게임플레이/UI에 요청, "읽었는데 헷갈렸다"면 헷갈린 부분을 문구에 보강 |
| 그 밖 | 그대로 |

- 문구는 Unity와 웹이 같은 `levels.js`의 `hint`를 쓰므로 한 번 바꾸면 `unity.sh levels`로 둘 다 바뀐다. 바꾼 뒤에는 2차 플레이테스트에서 같은 기준으로 다시 본다(전후 비교)
- 결정 결과와 근거(사람 수)는 `design/levels/playtest/<날짜>-decisions.md`에 적고 리드에게 보고한다
