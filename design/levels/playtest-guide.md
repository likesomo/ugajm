# 사람 플레이테스트 안내 (17스테이지, Unity WebGL / 웹 프로토타입)

목적: 흥미도 모델(`interest-model.md`)이 예측한 막힘·지루함 지점이 실제와 맞는지 확인하고, 가중치를 보정할 기록(`telemetry-mapping.md`)을 모은다. 그리고 6 숫자 문 보강과 힌트 문구 변경을 할지 7장 기준으로 결정한다.
대상: `7lucky` 3a37d11 기준 17스테이지 (석상 수 문 3개, 레버 2개 포함). 스테이지 맵은 b03a654 이후 바뀌지 않았다. 번호는 바뀔 수 있으니 분석은 스테이지 이름으로 한다.

두 빌드는 같은 `levels.js`(Unity는 export한 `levels.json`)와 같은 규칙(C# 이식, `verify`·골든 테스트로 일치 확인)을 쓰고, 같은 스키마로 같은 서버에 기록을 보낸다. 대시보드에서는 **클라이언트 필터**로 나눠 본다.

| | Unity WebGL (본 게임) | 웹 프로토타입 |
|---|---|---|
| 대시보드 `client` | `unity-webgl` | `web-proto` |
| `build` | `0.1.0+<커밋>` (`Application.version`) | `proto-<레벨 해시>` |
| 화면 | 3D 보드, 이동·미끄러짐 트윈 | 2D 격자, 즉시 반영 |
| 시작 | 타이틀 → 스테이지 선택 (`?level=1`이면 바로 1번) | 바로 1번 |
| 기록 끄기 | 설정 → "플레이 기록 보내기" (기본 켬) | 화면 아래 "기록 전송 켬/끔" |
| 서버 주소 | **빌드에 없음** (`AppConfig.telemetryEndpoint` 비어 있음) → URL에 `?telemetry=` 필수 | `localhost`면 자동으로 8787 |

조작은 같다: 방향키/WASD/옆 칸 클릭, K KEEP, X SWITCH, Z 되돌리기, R 재시작, H 풀이 보기, `[` `]` 스테이지, Enter 다음. Unity만 Esc = 스테이지 선택.

**어느 쪽으로 할지**: 본 게임 확인이 목적이므로 **Unity WebGL을 기본**으로 하고, 빌드가 깨졌거나 한 대의 PC로 빨리 돌릴 때 웹 프로토타입을 쓴다. 한 테스터는 한 빌드만 한다(두 번째 빌드는 이미 푼 퍼즐이라 기록이 무의미).

## 1. 준비 (진행자)

### 1.1 기록 서버 (공통)

```bash
export PATH="/c/Program Files/nodejs:$PATH"
STATS_TOKEN=<아무 문자열> node server/src/index.mjs
#   대시보드      http://localhost:8787/dashboard#token=<토큰>
#   웹 프로토타입  http://localhost:8787/play/        ← 같은 출처라 기록이 자동으로 쌓인다
```

### 1.2 Unity WebGL

```bash
unity/Tools/unity.sh build-webgl     # 에디터를 닫고. → Builds/WebGL/
unity/Tools/unity.sh smoke-webgl     # 보드가 그려지는지 확인 (build-webgl OK만으로는 못 거른다)
unity/Tools/unity.sh serve           # http://localhost:8090
#   테스터 주소   http://localhost:8090/?telemetry=http://localhost:8787
```
- 시작 전에 진행자가 한 번 열어 1스테이지에서 몇 걸음 움직이고, 대시보드의 클라이언트 목록에 `unity-webgl`이 생기는지 확인한다. 안 생기면 주소의 `?telemetry=` 를 빠뜨린 것이다
- 설정의 "플레이 기록 보내기"가 켬인지 확인 (예전에 끈 브라우저면 꺼져 있다)

### 1.3 공통 주의

- 진행 상황(클리어 기록)과 플레이어 ID는 브라우저 저장소에 남는다 → 사람마다 **시크릿 창**을 새로 연다
- 다른 PC의 테스터: `cloudflared tunnel --url http://localhost:8787`(서버). Unity는 게임 페이지용 터널을 하나 더(`--url http://localhost:8090`) 열고, 서버를 `ALLOWED_ORIGINS='*.trycloudflare.com'`로 실행한 뒤 `https://<게임 터널>/?telemetry=https://<서버 터널>`을 준다 (자세한 것은 `server/README.md`)
- 웹 프로토타입만 따로 띄울 때 `python -m http.server 8777`은 이 PC에서 8777 포트가 이미 쓰이고 있을 수 있다. 기록이 필요하면 항상 `/play/`를 쓴다
- 테스트 기간에는 스테이지와 빌드를 바꾸지 않는다. 바꾸면 `build` 값이 달라지므로 빌드 필터로 나눠 본다

## 2. 테스터에게 할 말 (이것만)

> 한 번에 7걸음만 걸을 수 있는 퍼즐입니다. 1번부터 순서대로 해 주세요. "풀이 보기"와 되돌리기는 언제든 써도 됩니다.
> 그만하고 싶으면 그때 그만두셔도 됩니다. 생각나는 건 소리 내어 말해 주세요.

- **규칙을 미리 설명하지 않는다.** 스테이지 시작 때 나오는 안내 문구(이하 "힌트 문구")가 규칙을 가르치는지 보는 것도 테스트다
- "풀이 보기"(H)는 힌트가 아니라 **처음부터의 최단 풀이 전체**를 보여 준다. 대시보드의 "힌트 본 비율"은 이 버튼이다. 힌트 문구를 읽었는지는 기록되지 않으므로 진행자 메모로만 안다
- 막혀도 도와주지 않는다. 테스터가 물으면 "풀이 보기를 써도 돼요"까지만
- 40~50분이면 17스테이지를 대부분 끝낸다. 시간 제한을 말하지 않는다
- 목표 인원: **5명 이상** (5명 미만인 스테이지는 보정에 쓰지 않는다)

## 3. 스테이지별로 볼 것

예측 흥미도 I와 모델이 의심하는 점이다. 진행자는 해당 스테이지에서 아래 질문의 답을 메모한다(시각, 한 줄). 특히 **힌트 문구를 읽은 직후 바로 풀었는지**(★)를 적는다. 7장 힌트 문구 결정에 쓴다.

## 4. 끝난 뒤 질문 (2분)

1. 가장 재미있던 스테이지와 이유
2. 가장 짜증났던 스테이지와 이유 (억울함 / 지루함 / 몰라서)
3. "아!" 하고 풀린 순간이 있었던 스테이지
4. 규칙 중 끝까지 헷갈린 것
5. 6번(숫자 문)에서 문의 숫자를 셌는가, 그냥 지나갔는가

답은 `design/levels/playtest/<날짜>-notes.md`에 사람별로 적는다(이름 대신 P1, P2…, 빌드 종류 표시). 대시보드의 플레이어 ID와 연결하려면 시작 시각을 함께 적는다.

## 5. 기록 넘기기

```bash
T=<토큰>; mkdir -p reports/telemetry
for C in unity-webgl web-proto; do
  curl -H "Authorization: Bearer $T" "http://localhost:8787/api/export/attempts.csv?client=$C&since=<날짜>" -o reports/telemetry/attempts-$C.csv
  curl -H "Authorization: Bearer $T" "http://localhost:8787/api/export/events.jsonl?client=$C&since=<날짜>" -o reports/telemetry/events-$C.jsonl
done
```
- `reports/`는 커밋하지 않는다. 레벨 디자인이 보정 스크립트로 읽어 `interest-curve.html`에 실측 I를 겹쳐 그린다
- 두 클라이언트는 같은 스테이지 이름으로 합쳐 본다. 단, 한 스테이지에서 둘의 클리어 시간 중앙값이 2배 넘게 차이 나면 합치지 않고 원인(표시·조작)을 먼저 본다

## 6. 성공 기준 (모델 검증)

- 8(레버 소개)에서 시간·재시작이 뛰고 9(멈춰 세우는 석상)에서는 v0보다 덜 막힌다 → 모델 맞음
- 7의 시간·idle이 3·8 수준이다 → 자동 난이도 보정(`dAdj`) 필요
- 13~15에서 HUD 석상 수를 보고 푸는가 → 아니면 화면 표시 강화 요청(게임플레이/UI)
- 실제 이탈이 가장 많은 스테이지의 예측 I가 기준선 근처(0.45 이하)인가 → 아니면 C·F 상수 보정(`telemetry-mapping.md` 3장)

## 7. 결정 기준: 6 숫자 문 보강과 힌트 문구 (`proposal-polish.md` 연계)

표본이 5명 안팎이므로 비율 대신 **"5명 중 몇 명"** 으로 판단한다(인원이 늘면 같은 비율로). 첫 시도만 센다. 대시보드 **스테이지 지표 표**와 **히트맵**, 그리고 4장 메모를 같이 본다. 결정은 레벨 디자인이 제안하고 사용자 승인 뒤에 스테이지를 바꾼다.

### 7.1 대시보드에서 볼 값

| 판단 | 대시보드 위치 | 값 |
|---|---|---|
| 6이 너무 쉬움 | 표 "클리어 시간 중앙", "클리어 이동 중앙" / `attempts.csv`의 `activeMs`, `moves`, `minMoves` | 테스터별로 activeMs < 20초 **그리고** moves ≤ 1.3×minMoves 인 사람 수 = **"쉬움 n"** |
| 6에서 문을 시험해 봄 | 히트맵 스테이지 6, 지표 "막힌 이동" | 숫자 문 칸의 막힘 횟수 (0이면 아무도 문 규칙을 건드리지 않음) |
| 8이 실제 급상승 | 표 "클리어 시간 중앙", "재시작/시도", "힌트 본 비율", "이탈률" | 8의 클리어 시간 중앙값 ÷ 7과 9 중 큰 값 = **"8 배율"**, 8에서 풀이 보기·이탈한 사람 수 |
| 힌트 문구가 답을 줌 | 4장 메모 ★ + `attempts.csv`의 `idleCount`, `activeMs` | 문구를 읽은 직후 idle 없이(`idleCount = 0`) 30초 안에 푼 사람 수 = **"즉답 n"** |
| 힌트 문구가 모자람 | 표 "힌트 본 비율", "몸 낭비", "몸 사용 사유" / 히트맵 "몸 낭비" | 풀이 보기·이탈한 사람 수 = **"막힘 n"**, 규칙 오해 흔적(`fell`·`vanish`·`crumble` 뒤 재시작) |

### 7.2 6 숫자 문

| 6의 실측 | 8의 실측 | 결정 |
|---|---|---|
| 쉬움 ≥ 3/5 **또는** 질문 5에서 "안 셌다" ≥ 3/5 | 8 배율 < 2 이고 8의 막힘 ≤ 1/5 | **6만 다듬기**: 몸 1개를 유지하되 숫자 문을 바닥으로 바꾸면 해가 막히도록(문을 세어야 풀리도록) 맵 수정. `proposal-polish.md` 1.1 마지막 항목 |
| 같음 | 8 배율 ≥ 2 **또는** 8의 막힘 ≥ 2/5 | **6 다듬기 + 8 원인 확인**: 1.1 탐색대로 6을 몸 2개로 올려 8을 받치는 맵은 없으므로 6은 위와 같이 다듬고, 8은 아래 "8이 막힐 때"로 처리 |
| 쉬움 ≤ 2/5 이고 문 칸 막힘 ≥ 1 (누군가 문을 시험함) | 8 배율 ≥ 2 또는 8의 막힘 ≥ 2/5 | **6은 그대로**, 8은 아래 "8이 막힐 때"로 처리 |
| 같음 | 8 배율 < 2 이고 막힘 ≤ 1/5 | **바꾸지 않음**. 모델의 8 최저점(0.36)이 과하게 낮았다 → C(`stretch`·`sigma`) 보정만 |

- 6을 다듬을 때 확인: 솔버로 풀림, 숫자 문을 바닥으로 바꾸면 최단 해가 달라지거나 막힘(`experiments/run.mjs`), 6의 예측 I가 0.55 아래로 떨어지지 않음, 7·8의 예측 I가 떨어지지 않음
- **8이 막힐 때**: 8의 문구는 이미 "발판과 달리 한 번 당기면 그대로다"라고 레버와 발판의 차이를 말한다. 그래서 메모로 원인을 가른다
  - 레버를 밟았는지, 벽이 내려갔는지 **못 봤다** → 표시 문제. 레버 상태·벽 변화 표시 강화를 게임플레이/UI·아트에 요청 (Unity에서만 그렇다면 확실)
  - 규칙은 알았는데 **몸 2개 계획**(당기는 몸 + 지나가는 몸)에서 막혔다 → 의도한 도전. 8의 예측 I는 기준선 위이므로 이탈 ≤ 1/5면 그대로 둔다
  - 이탈 ≥ 2/5 → 레버 소개를 5 바로 뒤로 옮기는 안(8은 0.61로 오르지만 멈춰 세우는 석상이 0.34로 떨어짐)과 실측을 놓고 다시 제안한다

### 7.3 힌트 문구

대상은 질문형 시안이 있는 **7 홀수의 저주, 9 멈춰 세우는 석상**(`proposal-polish.md` 2장)과, 결과에 따라 문구 보강이 필요할 수 있는 규칙 소개 스테이지 **3, 8, 11, 15**다.

| 실측 | 결정 |
|---|---|
| 즉답 ≥ 3/5 이고 막힘 ≤ 1/5 (문구가 답을 말해 버림) | **질문형으로 교체** (7, 9 시안). 규칙 소개 스테이지는 교체하지 않는다 |
| 막힘 ≥ 2/5 (풀이 보기·이탈) | **질문형 금지**. 지금 문구 유지, 3장 메모에서 오해한 규칙이 있으면 그 규칙을 더 직접 말하도록 보강 |
| 규칙 소개 스테이지에서 오해 흔적(같은 사유의 몸 낭비 2회 이상, 또는 `move.crumbled` 직후 재시작)이 있는 사람 ≥ 3/5 | 3·8·11·15의 지금 문구는 모두 규칙을 직접 말한다. 메모에서 "문구를 안 읽었다/못 봤다"면 문구 표시(위치·시간) 문제로 게임플레이/UI에 요청, "읽었는데 헷갈렸다"면 헷갈린 부분을 문구에 보강 |
| 그 밖 | 그대로 |

- 문구는 Unity와 웹이 같은 `levels.js`의 `hint`를 쓰므로 한 번 바꾸면 `unity.sh levels`로 둘 다 바뀐다. 바꾼 뒤에는 2차 플레이테스트에서 같은 기준으로 다시 본다(전후 비교)
- 결정 결과와 근거(사람 수)는 `design/levels/playtest/<날짜>-decisions.md`에 적고 리드에게 보고한다
